# Weekly Premium giveaway

Approved scope: implement weekly lifetime Premium giveaways, optional registered party members, a compact homepage banner, and recent winners on Premium pages.

Every Sunday at 20:00 Asia/Yekaterinburg (15:00 UTC) select one eligible solo listing and one eligible group listing. Each published listing has one ticket. Listings must be active, unmoderated, unexpired at the cutoff, created by an existing non-banned user. A party uses its explicitly selected registered members; if none are listed, its author receives the prize. Filter recipients who already have Premium or are banned. The solo winner cannot also receive the party prize. No donation records are fabricated: use the existing manual lifetime grant premiumGrantedAt.

Start the schedule on the first Sunday strictly after feature initialization, persist this cutoff, and advance it weekly. Never draw historical weeks from before initialization. If the service is briefly unavailable, process due weeks using each cutoff, without duplicate rewards. Persist selected winners before grants; retries must grant the same users and expose results only after successful grants. Empty categories have no winner and a truthful empty state. Use crypto.randomInt for uniform selection, no dependencies, no client-triggered draws. Unique draw keys protect concurrent backend instances. Use a recoverable processing lease and retained selected winners. The publication state at processing time is used with cutoff date filters; disclose that there is no historical snapshot reconstruction.

Group composition is optional, maximum ten unique registered user IDs and no more than groupSize. Solo listings cannot contain members. Existing drafts without memberIDs remain valid. Invalid or missing accounts must be rejected by the server. A bounded authenticated exact-name/prefix search displays existing public profile fields only. Store IDs and expose member public name/avatar in listing DTOs; members can be removed and edited, including old listings. Selection does not require new consent workflows or gameplay evidence.

Public API GET /api/support/giveaway returns {nextDrawAt, timeZone:'Asia/Yekaterinburg', latestDraw: null | {drawAt, solo:null|{userID,name,avatar}, group:null|{userID,name,avatar,groupName}}}. It must work without payment networks enabled or authentication and must not expose contacts, tokens, rejected candidates, or incomplete results. Return the most recently completed draw, labelled with its date (not always 'last week' if stale).

The UI explains two lifetime Premium prizes, Sunday timing, active listing eligibility, existing-Premium exclusion, party fallback, and one ticket per listing. Homepage CTA links directly to solo boards; party CTA links directly to group boards. Show rules on the board and Premium page so entrants know the conditions before posting. Winners link to public profiles. Render safely before asynchronous data arrives, with explicit empty, loading and failure states. Preserve SEO prerender and all six locales. No fake winners or production demo data.

No production deployment, push, paid provider configuration, external messages or Codex scheduled automation are part of this local implementation. Fake intent cannot be inferred reliably from publication alone; existing report/moderation and one slot per account remain the minimal protections.
