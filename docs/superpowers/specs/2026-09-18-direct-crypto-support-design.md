# Прямые криптовалютные переводы для поддержки Avalon

## Согласованный сценарий

Заменить создание новых OxaPay-счетов прямыми переводами на кошельки владельца. Пользователь выбирает сеть, переводит произвольную сумму и указывает txid в авторизованном аккаунте. Сервер проверяет поступление и учитывает фактически полученную сумму. Уникальная сумма и предварительная заявка перед переводом не требуются.

Txid не доказывает принадлежность перевода пользователю. По явно согласованному решению владельца первая успешно проверенная заявка получает начисление, а споры разбираются вручную. Повторно учитывать тот же перевод нельзя.

## Адреса получателя

| ----- | ----------------------- | ---------------------------------------------------------------- |
| BTC   | Bitcoin mainnet         | `bc1qn63r5d5qd0rnq7l9v2kp75rx9c5jsh9m22v09ru9dy3t3hutt8zqksv2nv` |
| USDT  | TRON / TRC20            | `TLmpR98uorxHmAULuG5JwDpaxKv7j5Zmvq`                             |
| USDT  | Ethereum / ERC20        | `0xE37cA64A14dD8e92929B7E71f3DA32267Da5969a`                     |
| USDT  | BNB Smart Chain / BEP20 | `0xE37cA64A14dD8e92929B7E71f3DA32267Da5969a`                     |

Адреса задаются серверной конфигурацией и публикуются через API. Приватные ключи и seed-фразы приложению не нужны. Каждая заявка сохраняет адрес получателя на момент создания, поэтому последующая смена конфигурации не меняет существующие заявки.

## Интерфейс

Сохранить существующую страницу поддержки, описание Premium, настройки анонимности и публичную ленту. Вместо суммы счёта и перехода на OxaPay показать выбор сети, адрес с копированием и поле txid с кнопкой проверки. Явно подписать сеть и принимаемый актив. Не ограничивать сумму существовавшим минимумом hosted invoice.

В истории показывать сеть, фактическую криптосумму, долларовый эквивалент после начисления и состояние проверки. Txid доступен только владельцу заявки; не включать его в публичную ленту. Существующие локализации обновляются вместе с интерфейсом.

На первом этапе автоматическая проверка выполняется по txid. Адрес отправителя сам по себе не выбирает конкретный перевод, особенно при выводе с биржи; для пользователя без txid показать инструкцию, где его найти, и возможность обратиться к владельцу для ручного разбора.

## Проверка блокчейнов

Серверные адаптеры только читают блокчейн. Адреса API и RPC задаёт оператор, пользователь передаёт только сеть и txid. Все запросы имеют таймауты, ограниченные повторные попытки и проверку структуры ответа. Ошибка провайдера не считается отсутствием платежа.

- **Bitcoin:** получать транзакцию через совместимый с Esplora API, суммировать выходы на сохранённый адрес получателя. Учитывать только транзакцию в каноническом блоке после одного подтверждения (уточнение владельца в ходе реализации). Проверять hash блока по высоте перед начислением. Считать сатоши целыми числами.
- **Ethereum и BNB Smart Chain:** проверять chain ID RPC, успешный receipt, канонический hash блока и финальность блока. Учитывать только события Transfer разрешённого контракта USDT на сохранённый адрес. Если RPC не поддерживает требуемую проверку финальности, сеть не выдаёт начисление и сообщает оператору проблему конфигурации. Не доверять символу токена, входным параметрам вызова или одному лишь адресу отправителя.
- **TRON:** получать успешный receipt через SolidityNode, учитывать только Transfer разрешённого контракта USDT на сохранённый адрес. Данные только FullNode без solidification не дают начисления.

Контракты и decimals фиксируются в конфигурации поддерживаемых активов и проверяются по первичным источникам при реализации. Для BNB Smart Chain явно указывается принимаемый вариант USDT, включая Binance-Peg, если выбран именно он; одноимённые токены автоматически не добавляются.

Несколько подходящих выходов или событий в одной транзакции суммируются в одно начисление для данной сети, актива и адреса получателя. Исходные количества хранятся строками целых минимальных единиц; расчёты выполняются без потери точности Number.

## Подтверждения, оценка и Premium

Предлагаемое правило оценки: USDT учитывается как $1 за токен. Для BTC сервер получает текущий BTC/USD при первом успешном завершении проверки подтверждений. Это курс на момент обработки сайтом, а не исторический курс блока; интерфейс и инструкция используют ту же формулировку. Курс, источник и время фиксируются вместе с начислением и позднее не пересчитываются. При недоступном или устаревшем курсе заявка ждёт повторной проверки.

Долларовый эквивалент округляется вниз до цента. Перевод меньше цента сохраняется с нулевым вкладом в долларовый итог; исходная криптосумма не теряется. Накопленные $10 дают Premium по существующему правилу. Ранее выданный вручную Premium остаётся независимым от взносов.

После ввода txid заявка сохраняется, затем проверяется сразу и фоновым обработчиком независимо от открытой страницы. Кнопка повторной проверки остаётся. Обработчик использует сохраняемые в MongoDB сроки следующей попытки и аренду обработки, чтобы перезапуск и несколько процессов не порождали конкурирующие начисления. Повторы с увеличением интервала; после семи суток без подтверждения автоматические повторы прекращаются, но ручная перепроверка доступна.

Не вводить ограничения, что перевод должен быть сделан после создания заявки: пользователь вправе сначала отправить деньги, затем ввести txid.

## Хранение и однократное начисление

Расширить SupportOrder провайдером direct, сетью, txid, адресом получателя, количеством минимальных единиц, данными блока и зафиксированной оценкой. Сохранить status=finished и sandbox=false для совместимости с текущими итогами, публичной лентой и Premium.

До подтверждения поступления заявка не резервирует перевод глобально. Уникальный идентификатор начисления строится из сети, нормализованного txid, актива и получателя. Уникальный индекс MongoDB и атомарное условное обновление не позволяют двум аккаунтам получить один перевод. Повторная отправка владельцем уже учтённого перевода возвращает существующий результат. Другому пользователю возвращается сообщение о ранее учтённом переводе без раскрытия аккаунта получателя.

Сумма Premium по-прежнему вычисляется из подтверждённых записей, а не отдельным увеличением счётчика. Сохранить ограничения частоты проверок на аккаунт; фоновые запросы обрабатываются ограниченными партиями. Некорректный txid отклоняется до запроса провайдера. Сетевые ошибки и недоступность RPC не меняют завершённое начисление.

## Ручное исправление

Добавить операторскую CLI-команду для переноса завершённого direct-начисления на существующий аккаунт по ID записи с обязательной причиной. Команда атомарно меняет владельца и добавляет в ту же запись историю: старый аккаунт, новый аккаунт, время и причина. Уникальный идентификатор перевода и сумма сохраняются. Общие суммы и Premium обоих пользователей пересчитываются через существующий ledger. Повтор команды не создаёт новый взнос. Настройку anonymous при переносе устанавливать в true, чтобы имя нового владельца не публиковалось без его решения.

## Совместимость и включение

По уточнению владельца во время реализации OxaPay не был подключён. Полностью удалить его код, callback, создание и перепроверку счетов, настройки, команды и ссылки в интерфейсе. Автоматическую миграцию с удалением данных не выполнять.

Новые сети включаются только с валидными адресами и рабочей конфигурацией чтения. Локальная разработка и автоматические тесты не должны обращаться к боевым платёжным API. Для оператора добавить инструкцию настройки, проверки доступности RPC, запуска фоновой проверки и ручного переноса. Деплой и настоящий тестовый перевод не входят в реализацию без отдельного запроса пользователя.

## Проверки реализации

- Валидные BTC, TRC20, ERC20 и BEP20 переводы; чужой адрес, поддельный токен, неверная сеть, failed receipt, недостаточная финальность и реорганизация до начисления.
- Сумма нескольких выходов/событий, разные decimals, большие целые количества, дроби меньше цента, недоступный курс BTC и неизменность сохранённого курса.
- Два конкурентных аккаунта с одним txid, повтор владельца, повтор фонового обработчика и рестарт процесса; проверка уникального индекса на MongoDB.
- Авторизация, отсутствие утечки txid/аккаунтов в публичных ответах, лимиты запросов и отсутствие запросов к пользовательским URL.
- Перенос между аккаунтами, журнал причин, пересчёт Premium и сохранение независимого ручного Premium.
- Настройки приватности, история и UI ошибок/ожидания/успеха.
