# Avalon → Selectel: Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Delegation is optional and requires applicable authorization.

**Goal:** Перенести Avalon на самый дешёвый проверенный вариант Selectel, сохранив рабочие данные, голос и восстановление пароля.

**Architecture:** Основной кандидат — один VDS 4-8-80 с Docker Compose: backend, MongoDB, nginx и LiveKit. Сайт и TURN используют общий IPv4 через TCP-прокси только после проверки совместимости; запасной вариант — отдельный VDS 1-2-25 для голоса. Внешние сервисы Yandex и существующий удалённый Codex worker сохраняются.

**Tech Stack:** Linux, Docker Compose, nginx, Node.js, MongoDB, LiveKit; HAProxy для кандидата с одним IP; Yandex Postbox HTTPS API; внешнее хранилище резервных копий.

**Spec:** [2026-10-10-selectel-migration.md](../specs/2026-10-10-selectel-migration.md).

## Global Constraints

- В каждый момент только один production-backend имеет право записывать в рабочую базу.
- Не переносить незавершённые партии: состояние игр находится в памяти backend.
- Не менять версию MongoDB одновременно с переездом.
- Не подключать тестовый backend к production LiveKit: запуск backend очищает комнаты.
- Сохранить ключи сессий, шифрования почты, почтовых событий и рабочие данные пользователей.
- MongoDB, LiveKit API и управляющие voice-endpoint не доступны из публичного интернета.
- TURN/TLS на TCP 443 и доступность из проблемных пользовательских сетей — обязательные условия запуска.
- Codex worker остаётся на существующем удалённом хосте.
- Object Storage с изображениями, Postbox и обработчик почтовых событий остаются в Yandex Cloud.
- Резервная копия должна храниться вне VDS; работоспособность подтверждается восстановлением.
- После появления новых записей в Selectel откат требует переноса этих записей обратно; одной смены DNS недостаточно.

## Решение, бюджет и сроки

Это план, а не выполненный переезд. Цены проверены по публичным страницам 10.10.2026; окончательную сумму проверить при заказе. Данные о текущей нагрузке взяты из предыдущего аудита в беседе, на этапе 1 их необходимо обновить.

| Вариант                            |  Серверы в месяц | Внешние копии: бюджетная оценка | Когда выбирать                                |
| ---------------------------------- | ---------------: | ------------------------------: | --------------------------------------------- |
| Один VDS 4-8-80                    |          1 100 ₽ |                       200–400 ₽ | Голос и сайт прошли проверку общего IP        |
| VDS 4-8-80 + VDS 1-2-25 для голоса |          1 350 ₽ |                       200–400 ₽ | Общий TCP 443 несовместим с нужными клиентами |
| Текущие две VM Yandex без бонуса   | ≈9 738 ₽ / 720 ч |                        Отдельно | Исходная оценка для сравнения                 |

Таким образом, ориентир после переезда — **1 300–1 500 ₽/месяц** либо **1 550–1 750 ₽/месяц** с отдельным голосом. Резерв на копии — оценка, не опубликованный тариф хранилища. AI, прежнее хранение изображений, почта, удалённый Codex worker, домен и сверхлимитный трафик в эти суммы не входят. Снижение именно этой части расходов относительно двух исходных VM — примерно 82–87%; точное сравнение сделать по одинаковому расчётному периоду и налогам.

Закладываем 2–3 рабочих дня на подготовку и репетицию, затем окно обслуживания с предварительным ориентиром 30–60 минут. Фактическое окно определяется временем пробного переноса с запасом. После переключения — 48–72 часа наблюдения; резерв старой инфраструктуры — до 7 дней. Это инженерная оценка, не гарантия срока.

В период репетиции оплачиваются обе площадки. Если прежняя оценка VM верна, три дополнительных дня работы Yandex стоят около 974 ₽ до учёта бонуса и различий тарификации. Остановка VDS Selectel не прекращает его оплату; после завершения теста ненужный VDS удаляется. Для Yandex отдельно проверить остаточную оплату дисков/IP после остановки.

## Этап 3. Устранить SMTP-зависимость — 0,5–1 день

**Почему до переключения:** `packages/backend/src/recovery/mail.ts` использует `postbox.cloud.yandex.net:465`; заменить только переменную окружения недостаточно. На VDS этот порт нельзя разблокировать запросом.

**Интерфейс:** сохранить существующий `(mail: Mail) => Promise<void>` для `RecoveryService`. Добавить переключатель `MAIL_TRANSPORT=smtp|postbox-api`, по умолчанию `smtp` для обратной совместимости.

- [ ] Добавить конфигурацию HTTPS-транспорта: `POSTBOX_ACCESS_KEY_ID` и `POSTBOX_SECRET_ACCESS_KEY`, сервисный аккаунт с правом `postbox.sender` в каталоге отправителя. Это статический ключ доступа для подписи API; не считать SMTP-пароль или API-ключ автоматически подходящим для AWS SDK.
- [ ] Использовать официальный `@aws-sdk/client-sesv2` с endpoint `https://postbox.cloud.yandex.net`, region `ru-central1`, `maxAttempts: 1`. Сформировать Raw MIME через существующий nodemailer в режиме `streamTransport`, сохранив UTF-8, отправителя Avalon и `Auto-Submitted: auto-generated`.

Контракт транспорта для реализации:

```ts
// Новый модуль recovery/postbox.ts; тип Mail импортируется из ./mail.
export interface PostboxConfig {
  accessKeyId: string;
  secretAccessKey: string;
  from: string;
}
// postboxSender(config) возвращает (mail: Mail) => Promise<void>.
// SESv2Client: endpoint выше, region 'ru-central1', maxAttempts: 1.
// SendEmailCommand: FromEmailAddress=config.from,
// Destination.ToAddresses=[mail.to], Content.Raw.Data=MIME Buffer.
// Общий дедлайн запроса: 20 секунд; никаких получателей/токенов в логах.
```

- [ ] В `index.ts` выбирать transport по конфигурации; при `postbox-api` не требовать SMTP-переменные, при `smtp` сохранить прежнюю проверку.
- [ ] Не отображать произвольный HTTP 4xx в SMTP 4xx: сейчас `service.ts` повторяет SMTP 4xx. Добавить явный признак допустимого повтора для документированного отказа до принятия письма; неоднозначные timeout/обрывы и HTTP 5xx автоматически не повторять. Ограничение числа попыток и существующие SMTP-тесты сохранить.
- [ ] Тестами с поддельным клиентом проверить: корректные MIME/адресат; успешную отправку; 400/401 без повтора; разрешённый rate-limit retry; timeout без повторной отправки; отсутствие секретов в ошибках; прежнее поведение SMTP. В live-тесте проверить письмо на собственный тестовый ящик и полный reset-flow.
- [ ] Проверить сохранение `MAIL_ENCRYPTION_KEY`, `MAIL_EVENT_SECRET`, suppression list и почтовой очереди. Обработчик `deploy/postbox-events/index.js` остаётся в Yandex и обращается к прежнему домену после смены IP.
- [ ] Собрать закреплённые образы вне production. Подготовить этот совместимый релиз и для старого Yandex, чтобы откат не упирался в другой формат конфигурации. Развёртывание на старом сервере тоже проводить после завершения партий.

Проверка локально после реализации:

```bash
npm run test --workspace=packages/backend -- --runInBand
```

**Переход дальше:** восстановление пароля и события почты проверены на Selectel через HTTPS. Публикация нового релиза выполняется по `deploy/README.md`; не запускать `npm version` только ради миграции — у команды есть release/push side effects.

- [ ] Использовать единый предикат в начале создания комнаты, перезапуска завершённой игры, старта обычной игры и создания/старта AI-комнаты. Для асинхронного AI-пути повторять проверку непосредственно перед регистрацией новой комнаты/запуском и корректно освобождать уже зарезервированный бюджет. Продолжение уже начатой игры, переподключение и её завершение остаются доступными.

```ts
// Новый файл packages/backend/src/maintenance/drain.ts
import { existsSync } from 'node:fs';
export function isDraining(): boolean {
  return existsSync('/run/avalon-ops/drain');
}
```

- [ ] Отказ оформлять через существующий механизм ошибок socket handlers; не оставлять необработанный Promise и не возвращать UUID несуществующей комнаты. Добавить понятное сообщение об обслуживании в используемые UI-переводы, если текущая обработка ошибки не показывает его.
- [ ] При включённом drain писать в закрытый операторский журнал раз в 10 секунд только полный список ID и состояний незавершённых комнат из `Manager.rooms`, включая AI, без чата/персональных данных. Это устраняет ограничение публичного списка 20 комнат. Ожидающие комнаты закрыть с уведомлением; начатые закончить.
- [ ] Проверить тестами: флаг включается/снимается без рестарта; create/start/restart/AI не обходят запрет; уже подключённый socket также получает отказ; текущая партия заканчивается и сохраняется; незавершённая 21-я комната видна в полном отчёте. В тестах файловый адаптер подменять, системный `/run` не изменять.
- [ ] Подготовительный релиз выкатывать по действующему порядку после завершения партий; если безопасное окно для него не наступило, отложить выкладку. На основном cutover включить drain заранее, затем ждать нулевого полного списка.

## Этап 4. Проверить сайт и голос на одном IP — 0,5 дня

**Результат:** выбран один подтверждённый вариант сети, а не предположение о совместимости TURN.

### Кандидат A: один VDS, 1 100 ₽/месяц

Использовать разные Docker network namespaces: nginx и LiveKit могут слушать внутренний TCP 443 каждый в своём контейнере. Только HAProxy публикует внешний TCP 443 и по TLS ClientHello выбирает назначение. TLS завершает соответствующий сервис.

```text
Публичный IP:443/TCP → HAProxy
  SNI имени TURN    → LiveKit:443, без PROXY protocol
  сайт/voice        → nginx:443, с PROXY protocol v2
nginx → backend:3000 и разрешённые voice RTC paths → backend:7882/TCP
backend → livekit:7880 внутри Docker
Интернет → LiveKit:7881/TCP и 7882/UDP
host watchdog → 127.0.0.1:7882/TCP → backend voice control
MongoDB доступна только backend по внутренней сети
```

- [ ] Создать `compose.yaml` с внутренними сетями, закреплёнными образами и именованными volumes. Backend и MongoDB — по одному экземпляру; не переносить `/var/lib/docker` со старого сервера.
- [ ] Настроить HAProxy TCP inspection с ограниченным ожиданием ClientHello и маршрутом TURN по реальному имени из инвентаризации. Для web использовать `send-proxy-v2`; для LiveKit не добавлять этот заголовок. Сервисы должны разрешаться после пересоздания контейнеров: фиксированные адреса отдельной Docker-сети или настроенный DNS resolver/reload.
- [ ] В nginx TLS-listener включить `proxy_protocol`, доверять только адресу HAProxy, восстановить `$remote_addr`; HTTP:80 обслуживать отдельно без PROXY-заголовка. Проверить, что клиент не может подделать IP через `X-Forwarded-For`; `TRUSTED_PROXY_CIDRS` backend ограничить nginx.
- [ ] Для LiveKit настроить `rtc.node_ip` на новый IPv4, `rtc.use_external_ip: false`, `rtc.tcp_port: 7881`, `rtc.udp_port: 7882`; убрать диапазон UDP при использовании mux. Объявляемые ICE-адреса должны совпасть с публичным IP и портами. TURN внутри контейнера слушает TLS 443 с сертификатом своего домена.
- [ ] Адрес LiveKit API для backend — `http://livekit:7880`, а не `127.0.0.1` внутри другого контейнера. Watchdog на хосте обращается к loopback TCP 7882; UDP 7882 — отдельный медиапорт, конфликта протоколов нет.
- [ ] Сохранить разрешённые nginx RTC paths из `nginx-voice.conf.example`; `/health/voice`, `/recovery/voice`, API LiveKit и токены не должны попадать в публичный доступ/логи.
- [ ] Обновить watchdog на новый compose/service, проверить stop/latch/recovery-протокол. Не копировать без изменений `gateway-firewall.sh`: он содержит старые интерфейсы/IP. Не выполнять исторический `activate-app.sh` с жёстко заданными образом и Yandex service units.
- [ ] Проверить два браузера, мобильный клиент, обычный UDP, TCP fallback и **принудительный TURN/TLS 443**. В тесте заблокировать прямой media-path и по ICE stats убедиться, что выбран именно relay, а не незаметный обход. Проверить сети РФ/Украины, Chrome/Firefox/Safari в поддерживаемых проектом версиях.

**Условие отказа от A:** клиент не передаёт необходимый SNI, relay не устанавливается, IP/rate limit ломается или сетевое поведение нестабильно. Не считать два успешных HTTPS-запроса доказательством работы TURN. Не отключать relay и не подменять обязательный 443 портом 5349 для экономии 250 ₽.

### Кандидат B: отдельный голос, 1 350 ₽/месяц за оба VDS

- [ ] Создать VDS 1-2-25 в той же локации; основной VDS остаётся 4-8-80.
- [ ] На основном IP оставить сайт и voice WebSocket gateway в nginx; TURN-домен направить на IP голосового VDS. LiveKit использовать с host networking, сохранив самостоятельный TCP 443 и привычную схему сертификатов.
- [ ] Связать VDS небольшим WireGuard-туннелем для LiveKit API и watchdog. Нативной private network у продукта нет. UDP-порт туннеля разрешить только между двумя публичными IP; API 7880 и gateway 7882 слушают/разрешены только на туннеле.
- [ ] Backend обращается к LiveKit API через туннель; watchdog на voice VDS — к backend control через туннель. Медиатрафик идёт по публичному IP voice VDS, не через туннель. Проверить маршрутизацию из Docker, MTU и отключение голоса watchdog при разрыве туннеля.
- [ ] Повторить весь набор voice-тестов, проверку сертификатов и доступности из проблемных сетей. Зафиксировать эту схему в `voice-separate.md`; убрать ненужный HAProxy из рабочего стека.

**Переход дальше:** выбранная схема воспроизводимо проходит проверки. Если обе схемы не прошли — DNS не переключать.

## Этап 5. Защита, ресурсы и резервное копирование — 2–4 часа

- [ ] Ограничить SSH административными адресами; внешний доступ открыть к 80/443 TCP, нужным media-портам и, для B, туннелю между узлами. MongoDB 27017, backend 3000, LiveKit API 7880 и voice control 7882/TCP закрыть снаружи.
- [ ] Проверить фильтрацию Docker published ports через forwarding/DOCKER-USER либо эквивалент выбранного firewall backend. Одних правил UFW INPUT недостаточно. Провести внешний TCP/UDP-тест разрешённых и закрытых портов; затем reboot и повторную проверку.
- [ ] Начать с прежних лимитов backend около 2 ГБ, MongoDB около 3 ГБ; для LiveKit ориентир 512 МиБ–1 ГБ с подтверждением тестом. Оставить ресурсы ОС/прокси/backup. Не снижать cache MongoDB вслепую; проверить конфигурацию и отсутствие OOM.
- [ ] Настроить ограничение container logs, например 100 МБ × 3 на контейнер; оставить текущий и предыдущий релиз образов. Не запускать `docker system prune --volumes`. Сборки и параллельное восстановление БД на рабочем 8 ГБ сервере не выполнять.
- [ ] При необходимости добавить 1–2 ГБ аварийного swap с низкой swappiness, отслеживать его использование; не считать swap заменой RAM.
- [ ] Для теста TLS использовать отдельные имена/ключи LiveKit. Для production заранее выпустить сертификаты через DNS challenge, сохранить автоматическое продление и права на DNS. Проверить reload каждого потребителя после renewal: nginx и LiveKit.
- [ ] Создать systemd unit для всего приложения с корректным запуском Docker/сетей/БД; voice watchdog оставить с прежними fail-closed гарантиями. Проверить восстановление после reboot без ручного входа.
- [ ] Настроить зашифрованную выгрузку MongoDB archive и необходимых конфигов/файлов во внешнее приватное хранилище. Практичный начальный вариант — отдельный backup-bucket в сохраняемом Yandex Object Storage с отдельным ключом, ограниченным этим бакетом.
- [ ] Установить ежедневный backup в тихое окно, 7 ежедневных и 4 еженедельных копии; применить lifecycle. Плановая потеря данных при аварии при такой частоте может составить до 24 часов. Если нужен меньший RPO, согласовать частоту/механизм до удаления исходного сервера; текущий helper кратко блокирует записи.
- [ ] Добавить уведомления: неудачный backup, копия старше 26 часов, RAM available <1 ГБ устойчиво, OOM/restarts, диск >70% и >85%, ошибки HTTP/voice, истечение сертификата <14 дней. Секрет расшифровки хранить вне сервера и проверить доступ к нему при аварии.

**Переход дальше:** сервер выдерживает тестовую нагрузку и reboot, закрытые порты закрыты, внешний архив скачивается и расшифровывается. Автоматических provider backups у данного VDS не предполагаем.

## Этап 6. Репетиция восстановления — 0,5 дня

**Результат:** проверенное время восстановления и доказательство пригодности копии.

- [ ] В согласованное тихое окно создать dump на исходном сервере штатным `deploy/voice/backup-mongodb.sh`. Он использует `fsyncLock`: gzip-проверка не заменяет restore, а блокировка не делает незавершённую бизнес-операцию атомарной.
- [ ] Передать архив по защищённому каналу, сравнить SHA-256, проверить расшифровку. Не публиковать содержимое production БД в Git/артефактах отчёта.
- [ ] Восстановить в **отдельный пустой** MongoDB volume на Selectel с той же версией MongoDB и совместимыми tools. Backend выключен, рабочая база Yandex не затрагивается. Проверить destination/volume перед любой командой `--drop`; предпочтительнее пустой новый volume.
- [ ] До запуска backend сравнить список баз/коллекций, количества документов, индексы, пользователей/роли БД и набор контрольных записей. Для TTL-коллекций учесть естественное истечение; при точном сравнении временно отключить TTL monitor на изолированной копии и обязательно вернуть после проверки. Не выводить персональные данные в отчёт.
- [ ] Измерить dump, передачу, restore, проверку и старт отдельно. Записать пиковую RAM/диск; должно остаться минимум 25 ГБ свободно, без OOM. Не запускать второй restore рядом с работающим production stack на том же VDS.
- [ ] **Не запускать полноценный backend на необработанной копии production для функциональных тестов.** Даже с `MAIL_ENABLED=false` остаются giveaway/support/rating workers. Для функционального стенда использовать отдельную чистую БД и тестовые учётные записи, тестовый LiveKit и отключённые платные/внешние интеграции, включаемые по одной для контролируемой проверки.
- [ ] Пройти вход, создание/завершение игры, чат, изображения, голос, reset password, support/webhook sandbox и удалённый Codex transport. Тестовые отправки и платные AI-вызовы ограничить контролируемыми сценариями; не запускать случайные production очереди.
- [ ] Выполнить проверку восстановления **из внешнего хранилища**, а не из ещё лежащего рядом локального dump. Сохранить время и контрольные результаты.

**Переход дальше:** выбранный VDS помещает восстановленные данные, полный функциональный стенд исправен, окно и процедура отката рассчитаны по репетиции.

## Этап 7. Подготовить окно переключения — за 24–48 часов

- [ ] Уменьшить TTL изменяемых A/AAAA/CNAME до 300 секунд; выждать прежний TTL до миграции. Не переносить NS/регистратора и не изменять MX/SPF/DKIM/DMARC одновременно с сервером.
- [ ] Подготовить точный список DNS-изменений: сайт/www, отдельные API/voice-имена при наличии и TURN. Если IPv6 на VDS отсутствует, заранее включить в переключение удаление старых AAAA; иначе часть клиентов продолжит ходить на Yandex.
- [ ] Предупредить пользователей об окне обслуживания и необходимости закончить партии. Назначить одного оператора переключения и вести журнал времени: freeze, backup, restore, new writes, DNS, решение об откате.
- [ ] Скачать финальные закреплённые образы, подготовить production-секреты и сертификаты. Проверить HTTP/TLS нового IP через `curl --resolve` для реальных доменов; браузерный тест до DNS проводить с явным локальным сопоставлением имён.
- [ ] Подготовить nginx maintenance-конфиг с 503 и Retry-After; публичные API/webhook также должны получать 503, а не успешную HTML-страницу. Проверить, что обработчик Postbox повторяет доставку событий после временного отказа.
- [ ] Проверить подготовленный на этапе 3 drain: оператор включает флаг без рестарта; новые комнаты/старты запрещены, текущие игры продолжаются. Перед freeze дождаться пустого полного списка незавершённых комнат, ожидающие комнаты закрыть с уведомлением.
- [ ] При выдаче 20 комнат не обходить fail-closed guard: использовать полный операторский отчёт drain из backend, либо перенести окно. Если механизм drain не готов, это блокирует заявленный перенос без потери текущих партий.

**Переход дальше:** все предыдущие условия выполнены, временной бюджет подтверждён репетицией, оператор знает оба сценария отката.

## Этап 8. Переключить production — целевое окно 30–60 минут

Оценка последовательности: закрытие/проверка 5–10 минут; финальный dump и передача 5–15; restore и сверка 5–15; запуск и smoke 10–20. Реальные значения подставить из репетиции; при превышении заранее выбранного окна до новых записей — откат по сценарию A.

1. [ ] При заранее включённом drain дождаться завершения партий, проверить полный список комнат. Включить maintenance на старом nginx, завершить старые WebSocket соединения и остановить **все** production backend/worker/cron-писатели; закрыть обходные прямые маршруты. Сам по себе HTTP maintenance не останавливает существующий WebSocket. На новом сервере держать drain включённым до открытия публичного входа.
2. [ ] Убедиться, что писателей нет и незавершённые записи завершились/остановились. Зафиксировать момент freeze. MongoDB оставить доступной только оператору для dump; не запускать одновременно старый и новый backend.
3. [ ] Создать **новый финальный** archive штатным helper, проверить успешное снятие `fsyncLock`, SHA-256, копию вне обеих VM. При ошибке unlock не удалять mutex вслепую — следовать `database-backups.md`.
4. [ ] Передать archive на Selectel, восстановить в новый пустой production volume при выключенном backend. Повторить сверку данных/индексов/ключей и проверить права приложения. Не использовать устаревший архив репетиции.
5. [ ] Зафиксировать точку перехода к сценарию отката B: **первый запуск нового backend уже может создавать записи фоновыми workers, даже до DNS**. Запустить выбранный production stack только после принятия этой точки.
6. [ ] Через локальное сопоставление доменов проверить сайт, вход старой учётной записью, историю, образы, голос, почту и private health/watchdog. Для smoke создания комнаты временно снять новый drain, оставив ingress закрытым для всех, кроме тестирующих адресов; завершить тестовую партию и вернуть drain до публичного открытия. Удаление тестовых данных должно быть заранее определено, не выполнять массовую очистку рабочей БД.
7. [ ] Переключить подготовленные DNS-записи, включая TURN и AAAA. Старый nginx оставить в maintenance: клиенты со старым DNS не должны попадать в работающий старый backend.
8. [ ] Проверить авторитетные DNS и несколько независимых резолверов, HTTPS/WebSocket и голос с реальных клиентских сетей. Снять drain и maintenance на новом сервере, открыть публичный вход и убедиться, что новые игры сохраняются там.
9. [ ] Проверить обработку накопившихся почтовых/support events, mail outbox, рейтингов и giveaway; не форсировать повторную обработку платежей/выдач без проверки идемпотентности.

**Переход дальше:** единственный рабочий backend в Selectel, контрольные данные на месте, новые записи сохраняются, UDP и relay проверены. Цель планового переноса — отсутствие потери подтверждённых записей за счёт остановки писателей; партии в памяти должны завершиться до freeze.

## Этап 9. Наблюдение и откат

### Наблюдение 48–72 часа

- [ ] В первый час проверять 5xx, авторизацию, соединения Socket.IO, voice joins/relay, watchdog и почту каждые 10–15 минут; далее использовать уведомления и проверки после пикового времени игры.
- [ ] Сравнить latency и ошибки с исходными измерениями; отслеживать OOM, available RAM, IO wait, диск, рестарты и трафик. Устойчивый CPU >70%, available RAM <1 ГБ или регулярный swap под обычной нагрузкой — повод пересчитать лимиты/размер, а не сразу покупать сервер вслепую.
- [ ] Проверить первую автоматическую внешнюю копию и её восстановление в изолированной среде, события почты, фоновые задачи, полную партию с голосом и повторные жалобы из Украины.

### Сценарий A: на новом сервере ещё не было записей

- [ ] Убедиться, что новый backend ни разу не стартовал либо доказано отсутствие любых новых записей. Остановить новый stack.
- [ ] Восстановить DNS из сохранённого набора, запустить старые backend/workers с прежней БД, проверить функции и убрать старые maintenance/drain.
- [ ] Новый сервер оставить закрытым для игроков. Проверить отсутствие двух писателей и сообщить об отмене окна миграции.

### Сценарий B: новый backend уже работал

- [ ] Включить drain в Selectel, закончить текущие партии, закрыть вход и остановить всех новых писателей. При аварии процесса партии в памяти могут быть уже потеряны — это отдельно фиксируется. Старый backend остаётся остановленным.
- [ ] Сделать новый согласованный dump **из Selectel** и внешнюю копию. Если БД недоступна, перейти к аварийному восстановлению с последнего пригодного бэкапа и явно оценить возможную потерю данных; обещать нулевую потерю в этом случае нельзя.
- [ ] Восстановить свежие данные на Yandex в отдельный volume совместимой MongoDB; прежний volume сохранить для расследования. Проверить данные и используемый совместимый релиз/секреты.
- [ ] Запустить Yandex stack, проверить его через явное сопоставление доменов, затем вернуть DNS, снять drain/maintenance и открыть вход. Selectel остаётся в maintenance.

Причины немедленно закрыть вход и оценить откат: признаки потери/расхождения данных, массовая невозможность входа, повторные OOM, неработающий TURN в нужных сетях, систематические 5xx. Отдельная локальная ошибка, которую можно исправить в пределах окна без риска для данных, не требует автоматического отката. DNS TTL не даёт строгого срока обновления у всех клиентов.

## Этап 10. Закрыть старые расходы — до 7 дней после переезда

- [ ] После 48–72 часов стабильности остановить ненужные Yandex VM, если это не мешает выбранному быстрому откату. Учесть, что старый maintenance после остановки недоступен клиентам с крайне устаревшим DNS.
- [ ] Перед окончательным удалением получить актуальный внешний backup, провести restore и сохранить финальные конфиги, release digest и runbook. Проверить, что архивы читаются без доступа к старой VM.
- [ ] Удалить только подтверждённо ненужные app/voice VM, их диски, IP и лишние snapshots после проверки зависимостей. Не удалять весь каталог/платёжный аккаунт Yandex.
- [ ] Сохранить Yandex Object Storage с UI-изображениями, Postbox, event-функцию и DNS, если они используются. AI Arena использует только существующий удалённый Codex worker. Проверить UI build manifest и наличие hashed assets.
- [ ] Обновить publish/deploy target и SSH allowlist удалённого worker; убрать старые адреса из мониторинга. После завершения периода отката отозвать временные migration credentials, не менять без отдельного плана ключи шифрования данных.
- [ ] Сверить фактические списания Selectel и остаток Yandex за первую неделю; зафиксировать ожидаемый полный месяц по одинаковому числу часов. Проверить отсутствие оплаты оставленного тестового VDS.

## Итоговый допуск к переключению

- [ ] Итоговая цена подтверждена, схема A или B выбрана по тестам.
- [ ] Новый IP проверен в сетях пользователей, испытывавших проблемы.
- [ ] Пароль восстанавливается через Postbox HTTPS, старые секреты сохранены.
- [ ] Голос работает через UDP и принудительный TURN/TLS 443.
- [ ] Новый стек и firewall проходят reboot, сертификаты автоматически обновляются.
- [ ] База восстанавливается из внешней копии, время известно, свободного места ≥25 ГБ.
- [ ] Production и тестовый LiveKit разделены; на копии production не запускаются случайные workers.
- [ ] Объявлено окно; учтены WebSocket, все писатели и гонка создания новых комнат.
- [ ] Оператор понимает границу новых записей и откат с обратным переносом БД.
