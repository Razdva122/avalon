# Миграции базы данных

[Documentation index](README.md)

Backend подключается к MongoDB, дожидается миграций и инициализации сервисов и только затем открывает HTTP-порт. Временные разрывы соединения обрабатывает драйвер MongoDB; дополнительные таймеры переподключения не создаются. Первичная ошибка соединения или миграции завершает процесс с ненулевым кодом, чтобы supervisor мог повторить запуск.

Версии находятся в `packages/backend/src/db/migrations/index.ts`. Применённые версии записываются в `schemaMigrations`. Для нового изменения сохранённой схемы добавляйте новую версию, не редактируйте уже применённую. `up` должен быть идемпотентным: процесс может остановиться между изменением данных и записью маркера завершения. Блокировка версии хранится в MongoDB, работает на standalone и не требует транзакций. Аренда продлевается каждую минуту; после аварийного завершения или потери связи она освобождается через 30 минут после последнего продления; второй запуск ждёт до двух минут и затем завершится с предложением повторить запуск.

При обновлении уникального индекса сначала проверяются исторические дубликаты. Затем строится новый уникальный индекс; прежний неуникальный индекс удаляется только после успешного создания ограничения. Имена индексов могут получить суффикс `_migration_v1`. Смена имени не влияет на уникальность. Автоматического удаления/слияния исторических данных нет. Сообщение об ошибке содержит коллекцию и поля, но не значения пользователей.

Перед обновлением сделайте штатную резервную копию. Если обнаружены дубликаты, остановите старые процессы записи и выясните происхождение записей. Пример **только для чтения** в mongosh, подключённом оператором к нужной базе:

```javascript
// Подставьте коллекцию и поля из безопасного сообщения миграции.
// Результат содержит только число конфликтующих групп, без ID пользователей.
db.getCollection('userachievements').aggregate(
  [
    { $group: { _id: { userID: '$userID', achievementID: '$achievementID' }, count: { $sum: 1 } } },
    { $match: { count: { $gt: 1 } } },
    { $count: 'duplicateGroups' },
  ],
  { allowDiskUse: true },
);
```

Не удаляйте запись миграции/блокировку, пока работает процесс, который её удерживает. Разрешение конфликтов — отдельная операторская операция после анализа и резервного копирования. После устранения причины обычный повторный запуск продолжит незавершённую идемпотентную миграцию.

Каталог встроенных достижений проверяется перед запуском обработчиков при каждом старте. Отсутствующие записи восстанавливаются через `$setOnInsert`; существующие требования сохраняются. Некорректное требование останавливает запуск с безопасной диагностикой, чтобы первая игра не заблокировала очередь рейтингов.

Recovery удаляет только просроченные элементы очереди/токенов через индексы времени истечения, не чаще раза в минуту на процесс. TTL-индексы на вложенные поля пользователя запрещены: MongoDB удалил бы весь документ аккаунта. TTL применяется только к отдельной коллекции счётчиков лимитов.

## После завершения переноса истории

Одноразовая миграция истории `2026-09-27-role-history-backfill-v1` выполнена на production в версии 66.1.2 и удалена из текущего кода. Графики читают только `role_rating_generations`; старые массивы `rolerankings` больше не используются. Текущая таблица лидеров `roleratings` остаётся резервным источником до первого успешного ночного пересчёта.

При восстановлении БД из копии, сделанной до переноса, сначала запустите версию 66.1.2 и дождитесь завершения всех трёх миграций, затем переходите на текущую версию. Новая пустая БД не требует переноса. Не удаляйте маркеры schemaMigrations: постоянные проверки индексов и каталог достижений продолжают использовать их.

Резервная копия и архивные коллекции исправленных дубликатов сохранены на production. Отчёт об операции: `production-database-repair-2026-09-27.md`.
