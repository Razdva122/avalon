## Как восстанавливается незавершённая игра

1. Архив сохраняется с `completionPending: true`. Ошибка первоначального сохранения повторяется из памяти живого backend.
2. Операция рейтинга добавляется с детерминированным ID игры. Все процессы могут помогать одной активной операции. Контроллер переключается на следующую только после завершения текущей; просроченная аренда не может нарушить этот порядок, поскольку очередь обходится без неё.
3. План сохраняется до изменения игроков. Значения каждого игрока применяются только при более новой `ratingSequence`. Повторный или запоздавший процесс не перезаписывает следующий результат или сброс.
4. После рейтингов обрабатываются достижения с той же последовательностью. Только затем операция считается завершённой. Фоновый worker продолжает незавершённые операции после рестарта.
5. Исторические результаты старой версии без журнала очереди не начисляются повторно автоматически: наличие такого результата не доказывает, что все его игроки были обновлены.

## Развёртывание и исторические данные

Не запускайте старый и новый backend одновременно: старые процессы не соблюдают новые правила записи рейтинга и AI-бюджета. Перед переключением сделайте согласованную резервную копию. Инструкции: `database-migrations.ru.md`, `ai-storage-retention.md`, `../deploy/voice/database-backups.md`.

При найденных дубликатах миграция останавливается с именем коллекции и полей. Она не удаляет и не выбирает произвольно исторические записи. Нужно проанализировать конфликтующие игры/результаты/достижения и затем повторить запуск. Повреждённые старые рейтинги нельзя надёжно восстановить одним count/update: требуются история партий и сведения о сбросах рейтинга. Это отдельная операция с рабочими данными.

Новый UI использует `getPlayerGameSummariesPage`; старый endpoint явно отказывает при истории больше одной страницы, вместо выдачи неполных итогов. Обновляйте backend и UI вместе. Общая статистика может отставать на время кэша — до минуты плюс длительность расчёта.

Граница гарантии: если первоначальная запись архива не состоялась и процесс был аварийно уничтожен, его память не является долговечным хранилищем. Для защиты всей активной игры от такого отказа нужна отдельная задача по журналированию игровых действий; текущая реализация гарантирует возобновление после успешного сохранения архива/операции.

## Проверки

Regression-тесты проверяют однократное завершение, повтор сохранения, параллельные начисления, прерывание посередине игроков, повтор достижения, сброс и запоздавшего обработчика, восстановление новой инстанцией worker, полный обход страниц и реальную сериализацию Socket.IO. Дополнительно проверяются миграции, планы запросов recovery, конкуренция достижений, поколения и очистка рейтингов, AI-резервы и аварийные ветви backup.

Заключительная проверка:

- Backend: **57 наборов, 406 тестов пройдено** (`npm test --workspace=packages/backend -- --runInBand`).
- UI: **166 тестов пройдено** (`npm test --workspace=packages/ui`).
- Backup: **5 тестов пройдено** (`python3 deploy/voice/backup-mongodb.test.py`).
- Backend TypeScript (`tsc --noEmit`), ESLint всех изменённых backend TypeScript-файлов и `git diff --check` прошли.
- UI собран штатным Vue CLI в development-режиме в `/tmp/avalon-database-ui-build`; production prerender в этом прогоне не запускался.
- Полный backend lint дополнительно обнаружил два существовавших до изменений `no-explicit-any` в `core/game/test/core/roles.test.ts` и `room/chat-endpoints.test.ts`. Обычный прямой UI `tsc` сообщает ошибки ambient-деклараций `.vue`; для проверки Vue-компонентов использована успешная штатная сборка.

Все интеграционные проверки выполнялись с искусственными данными во временных MongoDB. Отдельное ревью проверило конкуренцию очереди, реальные пакеты Socket.IO, публикацию/очистку поколений, AI-архивацию при истечении аренды и неоднозначный захват backup-блокировки; найденные блокирующие случаи исправлены и покрыты regression-тестами.
