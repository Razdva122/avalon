## 2. Подготовить Postbox

1. Откройте Postbox → Адреса → Создать адрес в каталоге выше.
2. Домен: `avalon-game.com`; описание: восстановление пароля Avalon.
3. Конфигурация: `avalon-password-recovery`.
4. DKIM: **Простая**. Postbox сам создаст и будет ротировать ключи.
5. Ограничьте отправителей одним локальным именем `security` (полный адрес `security@avalon-game.com`). Создайте адрес.
6. В карточке адреса скопируйте **обе** CNAME-записи DKIM, добавьте их в существующую DNS-зону `avalon`. Имена и значения берите из карточки — они уникальны. TTL 600. Не удаляйте вторую запись после проверки: она нужна для ротации.
7. Создайте TXT корня `avalon-game.com.`: `"v=spf1 include:spf.postbox.yandexcloud.net ~all"`. На момент проверки SPF отсутствовал. Если к моменту настройки уже появился SPF, объедините механизмы в одной записи: двух SPF быть не должно.
8. Создайте TXT `_dmarc.avalon-game.com.`: `"v=DMARC1; p=none; adkim=r; aspf=r"`, TTL 600. После проверки реальной доставки можно перейти на `p=quarantine`, затем `p=reject`. Не добавляйте адрес отчётов, пока нет рабочего входящего ящика.
9. В карточке отправителя дождитесь DKIM `Success`. A-записи сайта, NS, SOA и сертификаты менять не требуется. Postbox не создаёт входящий почтовый ящик.
10. Проверьте квоту Postbox для всего облака. Консоль указывает начальную квоту 200 писем в сутки; она общая с другими доменами, в том числе существующим `invitio.ru`. Для первого запуска приложение ограничено 20 письмами в час / 100 в сутки. Для роста запросите отдельное увеличение квоты с описанием транзакционного сценария.

Источник: [DNS Postbox](https://yandex.cloud/ru/docs/postbox/concepts/dns-records).

## 3. Создать отдельный SMTP-доступ и секреты

1. IAM → Сервисные аккаунты → Создать: `avalon-mail-sender`.
2. Назначьте `postbox.sender` в каталоге отправителя. Не выдавайте `editor` или `admin`. Роль на каталог может позволять отправку от других подтверждённых доменов этого каталога; ограничение адресов внутри Avalon не является изоляцией IAM между доменами.
3. Создайте API-ключ со scope **`yc.postbox.send`**. Сохраните ID и секрет в менеджере паролей. Это не статический S3-ключ и не IAM-токен.
4. `POSTBOX_SMTP_USER` = ID API-ключа; `POSTBOX_SMTP_PASSWORD` = секрет ключа. SMTP-сервер и TLS уже заданы кодом: `postbox.cloud.yandex.net:465`.
5. Сгенерируйте два разных случайных значения локально: `openssl rand -hex 32` для `MAIL_ENCRYPTION_KEY` и отдельный повторный вызов для `MAIL_EVENT_SECRET`. Результаты не отправляйте в чат и не коммитьте.
6. Храните секреты в защищённом хранилище оператора. При использовании Compose UI значения окружения сохраняются в метаданных ВМ и доступны людям с соответствующими правами. Не помещайте заполненный Compose в Git. Для функции предпочтительна привязка `MAIL_EVENT_SECRET` из Lockbox; её service account должен иметь `lockbox.payloadViewer` только на этот секрет.

Источник: [начало работы с Postbox](https://yandex.cloud/ru/docs/postbox/quickstart).

## 4. Подключить отказы и жалобы

Цепочка: Postbox → Data Streams в Serverless YDB → приватная Cloud Function → HTTPS API Avalon.

1. Создайте отдельную **Serverless** YDB `avalon-mail-events-ydb` и поток `avalon-mail-events`, тарификация по фактическому использованию. Это платные по использованию ресурсы; проверьте стоимость/лимиты перед созданием. Не создавайте выделенный кластер YDB.
2. В конфигурации Postbox `avalon-password-recovery` добавьте включённую подписку на этот поток: события **Bounce, Complaint**. Сохраните проверку стоп-листа и обязательный TLS. Привяжите конфигурацию к адресу Avalon, если ещё не привязали.
3. Создайте **непубличную** Cloud Function `avalon-mail-events`, Node.js 22, точка входа `index.handler`, память 128 МБ, таймаут 60 секунд. Загрузите только `deploy/postbox-events/index.js`: зависимостей npm нет. Не выдавайте `allUsers` права вызова.
4. Переменные функции: `MAIL_EVENT_URL=https://avalon-game.com/api/auth/mail-events`, `MAIL_EVENT_SECRET` — тот же секрет, что у backend. По возможности используйте ссылку на версию Lockbox, а не открытое значение в редакторе.
5. Создайте service account `avalon-mail-events-trigger`: `yds.admin` на выделенный поток (требование актуальной справки триггера), `functions.functionInvoker` только на `avalon-mail-events`. Не выдавайте общую роль `admin` на каталог. У оператора, создающего триггер, должно быть право использовать этот service account (`iam.serviceAccounts.user`).
6. Создайте Data Streams trigger на поток с этой функцией, накопление 1 секунда, размер пакета 1 байт (малый пакет, не обрезка сообщения), 5 повторов с интервалом 60 секунд. Подключите DLQ в Message Queue и права записи в неё для service account триггера. Очередь должна быть приватной. Если форма не позволяет настроить DLQ/повторы, используйте описанный в документации CLI, а до настройки не включайте отправку.
7. До готовности backend оставьте триггер выключенным. Затем включите его до первого реального письма. Проверьте число ошибок функции, отставание потока и сообщения DLQ. Настройте уведомления оператору: ошибки функции > 0, DLQ > 0, отставание потока > 5 минут. Для отправки уведомлений выберите существующий подтверждённый контакт оператора.
8. Функция принимает `{ "messages": [<событие Postbox>] }`, отправляет каждый адрес отдельно, удаляет из пересылаемого объекта тему/тело письма, использует Bearer-секрет. Любой сетевой сбой или не-2xx вызывает ошибку для повторной доставки. Повторная обработка безопасна.
9. После выкладки отправьте безопасное тестовое письмо на `spam+avalon-test@simulator.pstbx.ru`: симулятор возвращает постоянный отказ, событие должно пройти весь путь до `mailSuppressions`. `bounce@simulator.pstbx.ru` возвращает **временную** ошибку 452 и для теста Permanent Bounce не подходит.
10. Встроенного сценария Complaint у симулятора сейчас нет. Отдельно в тестировании приватной функции вызовите `{"messages":[{"eventType":"Complaint","complaint":{"complainedRecipients":[{"emailAddress":"avalon-complaint-test@example.com"}]}}]}` и проверьте suppression. Этот тест проверяет функцию/API, но не получение настоящей жалобы от провайдера. Адрес example.com здесь только строка в тестовом событии: письмо на него не отправляйте. Исчерпанные повторы разбирайте через DLQ. Адреса в Mongo хранятся как HMAC.

[Симулятор Postbox](https://yandex.cloud/ru/docs/postbox/concepts/mail-simulator).

[Схема интеграции](https://yandex.cloud/ru/docs/postbox/tutorials/postbox-webhook), [формат событий триггера](https://yandex.cloud/ru/docs/functions/concepts/trigger/data-streams-trigger), [создание триггера и DLQ](https://yandex.cloud/ru/docs/functions/operations/trigger/data-streams-trigger-create).

Изменения пока локальные в ветке `codex/password-recovery`. GitHub workflow публикует образы **по push нового тега** `v*.*.*`; ручной `workflow_dispatch` не публикует backend и UI-образы. На сервер workflow ничего не устанавливает.

1. Просмотрите diff, закоммитьте изменения и объедините ветку в релизную ветку обычным процессом проекта.
2. Проверьте GitHub Actions variable `DOCKER_HUB_USERNAME=razdva12` и secrets `DOCKER_HUB_ACCESS_TOKEN`, `YC_STORAGE_ACCESS_KEY_ID`, `YC_STORAGE_SECRET_ACCESS_KEY`. Секреты почты в GitHub для сборки не нужны.
3. Выполните проверки на Node.js 22:

   ```sh
   npm ci
   npm run test --workspace=packages/backend -- --runInBand
   npm run test --workspace=packages/ui
   node --test deploy/postbox-events/index.test.cjs
   npm run build:ui
   ```

4. Выберите **новый свободный** тег релиза. Не переиспользуйте `v61.6.0` и не передвигайте существующие теги. Пример команд (сначала замените значение):

   ```sh
   RELEASE_TAG=vX.Y.Z
   git tag "$RELEASE_TAG"
   git push origin "$RELEASE_TAG"
   ```

5. В GitHub → Actions дождитесь зелёного результата обоих jobs `publish-backend` и `publish-ui`. Проверьте наличие `razdva12/backend-avalon:<тег>` и `razdva12/nginx-avalon:<тег>` в Docker Hub. Не обновляйте ВМ, если прошёл только один job.

## 6. Подготовить безопасный Compose

В репозитории есть **фрагмент**, а не полная замена: `deploy/compose-mail.fragment.yaml`. Переносите изменения в копию текущей спецификации ВМ.

1. ВМ → Обзор → Спецификация docker compose. Сохраните текущую спецификацию в защищённом месте, включая прежние image tags. Она содержит секреты.
2. Перед остановкой сервиса сделайте согласованную резервную копию MongoDB и проверьте восстановление в отдельной тестовой БД. Cloud Backup у этой ВМ сейчас выключен. Снимок работающего диска без остановки/согласования MongoDB не заменяет проверенный backup. Для cold backup остановите приложение и MongoDB в согласованное окно, затем снимите диск.
3. Не меняйте название/путь `mongodb_data`, database name, Mongo credentials, image `mongo:6.0` или mounts сертификатов. Не запускайте `docker compose down -v` и не удаляйте volumes.
4. Новый nginx обращается к `backend:3000` через внутренний Docker DNS. Удалите публикацию `3000:3000` у backend; оставьте `expose: ['3000']` по желанию. Порты UI 80/443 сохраняются.
5. Используйте новую сеть `avalon-mail-net` для **всех трёх** сервисов, с подсетью `172.29.250.0/24` и фиксированным IP UI `172.29.250.10`. Сначала проверьте на ВМ `ip route` и `docker network ls`/`docker network inspect`: подсеть не должна пересекаться с существующими сетями/VPC/VPN. Если пересекается, выберите свободную и согласованно замените subnet, UI IP и `TRUSTED_PROXY_CIDRS`. Новое имя сети позволяет не менять IPAM уже существующей сети. Не удаляйте вручную сеть с работающими контейнерами.
6. В backend **добавьте** почтовые переменные из фрагмента к существующим. Сохраните платежные настройки и `SECRET_KEY`. Не генерируйте новые DB/JWT-секреты в рамках этой выкладки. `TRUSTED_PROXY_CIDRS` должен быть **только** фиксированным IP nginx `/32`, а не `0.0.0.0/0`.
7. Для первого применения: `MAIL_ENABLED=false`, `NODE_ENV=production`, лимиты `20`/`100`. Подставьте все секреты. `MAIL_ENCRYPTION_KEY` должен быть ровно 64 hex-символа, `MAIL_EVENT_SECRET` — отдельный случайный секрет не короче 32 символов. Не меняйте ключ шифрования между перезапусками: он также защищает стоп-лист.
8. В Compose литеральный `$` записывается как `$$`, включая уже существующие значения. Не меняйте существующее экранирование. Новые секреты удобно генерировать в hex, чтобы избежать интерполяции.
9. Если объединяете YAML вручную, не добавляйте второй ключ `environment` или `networks` внутри сервиса. Если старый environment — список `- KEY=value`, добавьте новые значения в таком же формате либо преобразуйте весь блок в mapping.

## 7. Применить через UI Yandex Cloud

Изменение сети и контейнеров прервёт активные игры/WebSocket-соединения. Выберите окно обслуживания.

1. Откройте `avalon-server` → **Редактировать** → блок Docker Compose. Вставьте подготовленную **полную** спецификацию, заменив оба image на один опубликованный тег. Не нажимайте создание новой ВМ.
2. Проверьте сохранение диска, IP, volumes и сертификатов; сохраните изменение. Если консоль требует остановку/перезапуск ВМ, выполните в этом же окне обслуживания.
3. Дождитесь Running и завершения загрузки контейнеров. При проблеме смотрите консоль/SSH, не создавайте новую пустую MongoDB.
4. Подключение для диагностики: `ssh -l razdva 158.160.115.216` (нужен ваш существующий SSH-ключ). Выполните:

   ```sh
   sudo docker ps
   sudo docker exec nginx nginx -t
   sudo docker logs --tail 100 backend
   curl -fsS https://avalon-game.com/api/auth/recovery
   curl -I https://avalon-game.com/password-recovery/
   ```

   Ожидается `{"enabled":false}`; страница 200 с `Cache-Control: no-store`, `Referrer-Policy: no-referrer`, `X-Robots-Tag: noindex, nofollow`. Не публикуйте содержимое логов без проверки на секреты.

5. Проверьте логин существующим аккаунтом, создание/вход в игровую комнату и платежную страницу. Проверьте, что 3000 больше не опубликован в `docker ps`, nginx разрешает `backend` во внутренней сети, и сайт доступен снаружи по HTTPS.
6. Убедитесь, что DKIM Success, SMTP-ключ сохранён, подписка/функция/триггер/DLQ готовы. Теперь в том же Compose поменяйте только `MAIL_ENABLED=true`, сохраните, дождитесь перезапуска backend. Включите триггер событий до тестовых писем. `/api/auth/recovery` должен вернуть `{"enabled":true}`.
7. На собственном тестовом аккаунте запросите восстановление. Проверьте доставку и заголовки Authentication-Results (DKIM/DMARC pass), срок ссылки и успешную смену пароля. Пароль меняйте сами. Повторное применение ссылки должно отклоняться, старые сессии — перестать работать, уведомление о смене пароля — прийти.
8. Проверьте неизвестный email: интерфейс отвечает так же, письмо не отправляется. Повторный запрос через несколько секунд не должен создавать новое письмо. Проверяйте ограничения на тестовом аккаунте, не рассылайте запросы пользователям.
9. Выполните тест Bounce/Complaint из раздела 4 и убедитесь в обработке событий. Без этого настройка антиспама не считается завершённой.

## 8. Наблюдение и откат

В первые сутки проверяйте Postbox: количество писем, недоставки, жалобы и квоту; Cloud Function: ошибки; Data Streams: отставание; DLQ: наличие сообщений. В backend события `mail_sent`, `mail_failed`, `mail_retry`, `mail_global_limit`, `mail_worker_failed` не содержат адресов или ссылок. Настройте алерт на первые ошибки и рост отказов. После стабильного старта поднимайте лимиты только вместе с проверкой облачной квоты.

Быстро остановить почту: `MAIL_ENABLED=false` в Compose и перезапуск backend. Игровой сервис продолжит работать, UI восстановления покажет недоступность. Отключённый backend отвечает 503 обработчику событий: при длительной паузе выключите триггер, сохраните события/DLQ и после восстановления обработайте их.

После первого успешного сброса пароля нельзя возвращать старый backend `v61.6.0`: он не проверяет `authVersion` и может снова принять старые сессии. Оставляйте новый backend с выключенной почтой и выпускайте исправление. Возврат старого UI тоже требует совместимой настройки nginx/портов; не открывайте 3000 ради отката без отдельного решения. Ключ шифрования и записи `mailSuppressions` при откате сохраняйте.

- Жалоба и постоянный отказ создают suppression, очередь ошибок пуста.
- Новый backend/UI одного релиза работают; Mongo volume прежний; порт 3000 снаружи закрыт.
- Проверены обычный вход, игровые WebSocket и инструкции остановки почты.
- Настроены мониторинг и уведомления конкретному оператору.
