# Голосовой чат комнаты · beta

На уровне сервера голос выключен по умолчанию. Перед включением `VOICE_ENABLED=true` пройдите реальные проверки ниже: одного успешного unit-теста недостаточно, чтобы доказать отзыв доступа или работу WebRTC/TURN.

Beta рассчитана на один процесс backend: допуски хранятся в памяти этого процесса. Несколько реплик или rolling deploy требуют отдельной координации допусков и не поддерживаются этой конфигурацией. LiveKit должен быть выделен только для Avalon: при запуске backend удаляет все оставшиеся комнаты этого экземпляра.

В настроенном окружении голосовой чат доступен во всех комнатах сразу: ведущему не нужно его включать, общих настроек и переключателя комнаты нет. Игрок сам подключается к голосу и включает свой микрофон; при подключении микрофон выключен.

После окончания обычной партии комната и голос сохраняются ещё 30 минут для обсуждения. При запуске следующей партии разговор старой комнаты закрывается; к новой комнате игрок подключается отдельно. В архивных играх панель голоса скрыта. Перезапуск backend завершает живые голосовые сессии.

## Схема размещения

На отдельной VM Yandex Cloud работает закреплённый `livekit/livekit-server:v1.13.7` из [Compose-шаблона](../deploy/voice/compose.yaml). Этот экземпляр LiveKit выделен **только** для Avalon: при старте backend удаляет все комнаты LiveKit, прежде чем объявить voice control готовым. Backend приложения на существующей VM запускает шлюз signaling на TCP `7882`. Публичный `wss://voice.example.com/` завершается TLS-прокси **на стороне backend** и перенаправляет только `/rtc`, `/rtc/validate`, `/rtc/v1`, `/rtc/v1/validate` на шлюз. Шлюз проверяет действующую сессию приложения и допуск к комнате при каждом новом подключении и переподключении. Backend обращается к LiveKit API по приватному адресу `http://<media-private-ip>:7880`; клиенты никогда не получают доступ к этому порту напрямую. Медиа идут от браузера к LiveKit по ICE/TURN, без Socket.IO.

Публичный URL шлюза и приватный API адрес — разные настройки. Если LiveKit и backend временно находятся на одной машине, `LIVEKIT_INTERNAL_URL=http://127.0.0.1:7880` подходит. Для двух VM задайте адрес LiveKit внутри VPC. Доступ к TCP `7880` разрешите **только** исходящему приватному IP backend VM. Media VM должна обращаться к `GET http://<backend-private-ip>:7882/health/voice` для watchdog. Если backend в Docker, `VOICE_GATEWAY_HOST=0.0.0.0` слушает внутри контейнера: nginx ходит к `backend:7882` по Docker-сети, а порт на host привязан лишь к приватному IP (`<backend-private-ip>:7882:7882`). Security group и host firewall пропускают на него только media VM; публичный IP backend VM и интернет не имеют доступа. Если backend запущен прямо на host, задайте `VOICE_GATEWAY_HOST=<backend-private-ip>` и разрешите локальному nginx обращаться по этому IP. Проверка health не требует секретов, поэтому сетевое ограничение обязательно.

## Подготовка media VM

1. Выделите отдельную папку Yandex Cloud для голоса или пометьте VM, диск и IP одной меткой `service=avalon-voice`. Запишите folder ID, VM ID, disk ID, public IP ID, время старта и размер VM для отчёта о расходах.
2. Создайте DNS `turn.example.com` на публичный IP media VM и выпустите доверенный TLS-сертификат для этого имени. Установите `fullchain.pem` и `privkey.pem` в `deploy/voice/tls/` на VM; доступ к приватному ключу ограничьте. Обновление сертификата должно обновлять эти файлы и перезапускать контейнер, иначе TURN/TLS перестанет работать после истечения срока. На media VM **нет** публичного signaling домена.
3. Скопируйте [`livekit.yaml.example`](../deploy/voice/livekit.yaml.example) в `livekit.yaml` на VM. Замените домен, API key и случайный API secret длиной не менее 32 символов. Ровно та же пара должна быть задана backend через `LIVEKIT_API_KEY` и `LIVEKIT_API_SECRET`. Файл с секретом и каталог `tls/` игнорируются Git и не добавляются в образ. Ограничьте права файлов. `rtc.use_external_ip: true` использует STUN для публичного адреса; проверьте объявленный ICE candidate. Если STUN определяет неверный адрес, задайте `rtc.node_ip` явно и выключите `use_external_ip`.
4. На media VM запустите `docker compose -f deploy/voice/compose.yaml config` и `docker compose -f deploy/voice/compose.yaml up -d`. Compose использует host networking, как рекомендует LiveKit для WebRTC. Отдельные Redis, SIP, ingress, egress и запись для этой beta не включаются.
5. В security group и host firewall разрешите от интернета TCP `7881` (ICE/TCP), UDP `50000–60000` (прямой ICE) и TCP `443` (TURN/TLS). TCP `7880` — только от backend VM по приватной сети. SSH — только с административных адресов. Не открывайте `7882`, API `7880`, метрики или debug endpoint публично. TURN здесь слушает TCP `443` прямо на media VM, с отдельным доменом и сертификатом; TLS signaling на TCP `443` остаётся на **другой**, backend VM. Если меняется схема с балансировщиком, заново проверьте рекламируемый TURN порт.
6. Установите [watchdog](../deploy/voice/watchdog.py) и [systemd unit](../deploy/voice/avalon-voice-watchdog.service) на media VM по пути `/opt/avalon/deploy/voice/`. Скопируйте [пример окружения](../deploy/voice/watchdog.env.example) в `/etc/avalon-voice-watchdog.env`, замените `BACKEND_PRIVATE_IP`; ограничьте файл и установите unit в `/etc/systemd/system/`. После `systemctl daemon-reload` запустите `systemctl enable --now avalon-voice-watchdog`. Его HTTP-запрос идёт напрямую по приватной сети, без системного proxy. Он ожидает `204` от backend health, который означает свежий control lease и отсутствие незавершённых удалений. Через примерно 10–14 секунд подряд без здорового ответа watchdog выполняет `docker compose stop livekit` и записывает постоянный флаг `/var/lib/avalon-voice-watchdog/latched`. Затем запускается автоматическое восстановление по протоколу ниже. Watchdog также проверяет, что контейнер LiveKit работает: остановленный контейнер запускает тот же протокол, даже если backend ещё отвечает `204`. Не разрешайте другим сервисам автоматически запускать LiveKit в обход watchdog.

Для прокси backend используйте [nginx-фрагмент](../deploy/voice/nginx-voice.conf.example) внутри отдельного TLS server блока `voice.example.com`. Потребуется действительный сертификат для этого домена. Добавьте указанную в шаблоне `limit_req_zone` один раз в `http` контекст; RTC location отвечает `429` при превышении частоты по исходному IP. Если перед nginx есть балансировщик, настраивайте real IP только для его доверенных адресов, не принимайте произвольный `X-Forwarded-For`. RTC location отключает access log и направляет error log в `/dev/null`, поскольку сообщения об upstream ошибках могут включать query string с токеном. Состояние диагностируйте через отдельные приватные health/metrics endpoints и агрегированные счётчики без URL; проверьте также логи внешнего балансировщика, CDN и APM. Не направляйте `/rtc` напрямую на LiveKit `7880`. Не добавляйте catch-all proxy на LiveKit: его HTTP API и служебные пути должны оставаться приватными. `GET /health/voice` не добавляйте в публичный nginx. Проверяйте синтаксис nginx до перезапуска.

## Конфигурация backend

Параметры перечислены в [шаблоне backend](../packages/backend/.env.example) и [справочнике окружения](environment.md). `VOICE_ENABLED=false` оставьте до прохождения проверок. При отдельной media VM `LIVEKIT_INTERNAL_URL` указывает на её приватный адрес, `LIVEKIT_PUBLIC_URL` — `wss://voice.example.com/`. Шлюз слушает отдельный порт `VOICE_GATEWAY_PORT=7882`; `VOICE_GATEWAY_HOST` задаёт его интерфейс. Пара API key/secret должна соответствовать media VM. Не передавайте секрет в UI, URL или diagnostic response.

## Проверка перед открытием beta

1. Проверьте из backend VM доступ к media VM `7880` и отсутствие доступа к нему из интернета. С внешней сети убедитесь, что `https://voice.example.com/` и неожиданные пути дают `404`, а прямой доступ к `7880`/`7882` закрыт. В логах прокси не должно быть query string с токеном.
2. Создайте тестовую комнату в окружении с настроенным голосом, посадите два **разных** тестовых аккаунта за стол. Запустите backend, LiveKit и шлюз. Из корня репозитория задайте `VOICE_SMOKE_ROOM_ID`, `VOICE_SMOKE_SOCKET_URL` и `VOICE_SMOKE_PLAYER_A_LOGIN`/`_PASSWORD`, `VOICE_SMOKE_PLAYER_B_LOGIN`/`_PASSWORD`, затем `node deploy/voice/smoke.cjs`. Вместо пароля можно передать локальные тестовые `VOICE_SMOKE_PLAYER_A_TOKEN`/`VOICE_SMOKE_PLAYER_B_TOKEN`. Скрипт не печатает токены, но хранит их в памяти процесса. Он запускает Chromium с подставными медиаустройствами, проверяет доставку аудио, отсутствие видео/data у второго участника, затем завершение медиа и повторный вход со старым токеном после `leaveVoice`. Пароли/токены не сохраняйте в shell history или Git.
3. Отдельно проверьте игрока, зрителя, ведущего без места, администратора сайта, гостя и пользователя другой комнаты через UI/Socket.IO. Зритель и ведущий без места не получают `joinVoice`. У администратора есть видимое обычное подключение. Проверьте потерю места, выход из комнаты, отзыв авторизационной сессии, замену активной голосовой сессии и перезапуск комнаты. Для каждого случая старый JWT, в том числе обновлённый SDK, должен отвергаться при начальном входе и полном reconnect. При пропаже управляющего Socket.IO медиа должно отключиться.
4. Проверьте два независимых браузера и третьего зрителя: слышимость, master/per-user volume, локальный mute, старт с выключенным микрофоном, отказ разрешения, отсутствие устройства, уход со страницы, мобильный autoplay. Проверьте прямой UDP и принудительный TURN fallback из сети с закрытым UDP; убедитесь, что TURN использует доверенный сертификат `turn.example.com:443`. После выхода браузер не должен продолжать захватывать микрофон. Проверка только на localhost не доказывает внешнюю доступность ICE/TURN.

Для проверки контракта gateway без MongoDB есть отдельный [реальный fixture](../deploy/voice/real-gateway-smoke.cjs). Запустите LiveKit v1.13.7 с локальными тестовыми API key/secret, HTTP портом `17880`, `rtc.use_external_ip: false` и `rtc.node_ip`, достижимым для Chromium на этой машине. Передайте `LIVEKIT_TEST_INTERNAL_URL`, `LIVEKIT_TEST_API_KEY`, `LIVEKIT_TEST_API_SECRET` и запустите `node deploy/voice/real-gateway-smoke.cjs`. По умолчанию fixture использует `http://127.0.0.1:17880` и опубликованные в самом fixture **локальные тестовые** ключи. Он не подходит для production-секретов и не подменяет проверку реальных ролей/сессий приложения. Fixture проверяет настоящий WebRTC с oscillator microphone, запрет камеры/data, завершение удалённого трека при отзыве, replay исходного/обновлённого JWT и очистку всех комнат при быстром перезапуске backend.

Если шлюз не может прекратить уже установленное медиа, SDK допускает повторный вход с обновлённым токеном, либо любой публичный путь обходит проверку, beta остаётся выключенной до исправления контракта отзыва.

При падении backend или потере связи с ним уже установленное WebRTC медиа может продолжаться до остановки LiveKit watchdog. Это ограниченное окно порядка 15–30 секунд, а не мгновенный отзыв при сетевом разделении. Проверяйте этот сценарий отдельным тестом: во время разговора остановите backend или запретите его VPC связь с media VM, засеките время до прекращения аудио, затем убедитесь, что при недоступном backend LiveKit остаётся остановленным, а после восстановления связи запускается только через описанный ниже протокол. Если media VM не может остановить контейнер, watchdog повторяет команду и пишет ошибку в journal; это инцидент, требующий немедленного ручного вмешательства.

### Автоматическое восстановление

Watchdog подтверждает остановку контейнера и отправляет `POST /recovery/voice` на **тот же приватный адрес backend**, что используется для health. Этот endpoint нельзя добавлять в публичный nginx: он доверяет ограничению TCP 7882 по IP media VM. Backend синхронно закрывает допуски, отменяет незавершённые входы, отзывает действующие голосовые сессии и заменяет внутренние имена комнат. Включённая настройка голоса за столом сохраняется; подключиться потребуется заново. Игровые комнаты не перезапускаются.

Только после ответа `204` watchdog запускает существующий контейнер LiveKit (`docker compose start livekit`). Backend повторяет очистку всех старых комнат выделенного LiveKit. До её завершения голос недоступен; результат старой, начатой до восстановления очистки не может открыть вход. После очистки и завершения отложенных отзывов `/health/voice` возвращает `204`. Watchdog проверяет также работающий контейнер и удаляет `latched`.

Если за 30 секунд восстановление не подтверждено, watchdog снова останавливает LiveKit. Неудачные попытки повторяются с паузами 30, 60, 120, 240 и далее по 300 секунд. Таймауты HTTP и Docker добавляются к этим интервалам. Флаг сохраняется при сбоях и перезапуске watchdog: новая попытка снова начинается с подтверждённой остановки. Ошибка остановки не разрешает запуск. Ответ старого backend (`404`), редирект или любой ответ, отличный от `204`, оставляет голос закрытым.

Для планового отключения сначала остановите watchdog (`systemctl stop avalon-voice-watchdog`), затем LiveKit (`docker compose -f /opt/avalon/deploy/voice/compose.yaml stop livekit`). Чтобы вернуть автоматическое управление, запустите watchdog. Одной ручной остановки LiveKit при работающем watchdog недостаточно: он восстановит контейнер.

### Выкладка изменения

1. Выпустите backend с `/recovery/voice` через существующий механизм metadata / yc-container-daemon. Docker Compose, ключи LiveKit и адреса менять не требуется. Перезапуск backend согласуйте на время без активных партий.
2. Обновите `/opt/avalon/deploy/voice/watchdog.py` на media VM и перезапустите только `avalon-voice-watchdog`. Сохраните предыдущий скрипт для отката. Если голос был заблокирован старым watchdog, новый восстановит его через приватный endpoint.
3. Проверьте `204` на `/health/voice` с media VM, отсутствие `latched`, работающий LiveKit и публичный `404` на `/recovery/voice` и `/health/voice`. Сам `POST /recovery/voice` не используйте как read-only проверку: он отключает текущие голосовые сессии.
4. Отказные проверки (перезапуск backend, потеря связи, ошибка очистки и перезапуск watchdog во время восстановления) выполняйте на отдельном экземпляре. Продовый restart-тест требует отдельного окна. При откате backend до версии без нового endpoint восстановите старый watchdog либо оставьте голос остановленным до ручной диагностики.

Проверки кода: `python3 -m unittest discover -s deploy/voice -p watchdog_test.py` и `npm test --workspace=packages/backend -- --runInBand src/voice`. Они проверяют протокол и отзыв допуска, но не заменяют проверку прекращения реального WebRTC-аудио при сетевом разделении.

## Расходы в первые 3–5 дней

Запишите начало и конец измерения с часовым поясом, конфигурацию VM и перечисленные resource IDs. В Yandex Cloud Billing откройте **Детализацию**, отфильтруйте папку или метку голоса, выберите период и сделайте разовую поресурсную CSV выгрузку. Сведите по отдельности VM (vCPU/RAM), диск, публичный IP, исходящий интернет-трафик и платный мониторинг, если он включён. Отдельно покажите скидки/гранты и фактическую сумму к оплате. Биллинг может обновляться с задержкой, поэтому рядом с отчётом укажите время последней проверки.

Сопоставьте начисления с числом голосовых сессий, участнико-часами и исходящим трафиком media VM. Снимайте сетевые счётчики по интервалам; после перезапуска VM они сбрасываются. Не суммируйте TURN и сетевой исходящий трафик как два независимых объёма. Покажите стоимость инфраструктуры в сутки и ориентир за 30 дней при **той же** нагрузке; прогноз не является лимитом или гарантией. Автоматическая регулярная выгрузка и бюджетное отключение для beta не настроены.
