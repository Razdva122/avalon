# Ручной frontend-аудит avalon-game.com

Дата: 21 сентября 2026. Проверена опубликованная версия **63.7.0**; версия в локальном package.json — **63.8.0**. Изменения приложения не вносились.

## Вывод

Prerender и критический CSS обеспечивают быстрый первый экран. Главные проблемы — промежуток между видимым и работающим интерфейсом, полноразмерные картинки в маленьких иконках, тяжёлый иконочный шрифт и большой общий CSS. Начинать с переписывания приложения или смены фреймворка оснований нет.

Подтверждён потерянный ранний клик: в 391 мс кнопка Create room уже видна, приложение ещё не смонтировано; клик в 418 мс не открыл форму даже после гидратации. В трёх отдельных последовательных прогонах гидратация завершалась через 4,71–4,86 с. Это ощутимая проблема, которую хороший LCP не показывает.

## Методика и границы

- Chrome через Puppeteer/CDP, публичный production; просмотр сети, PerformanceObserver, Coverage, проверка HTTP-заголовков и исходников.
- Пять URL: `/`, `/ru/`, `/wiki/rules/`, `/wiki/roles/merlin/`, `/support/`; каждый в мобильном и настольном профиле.
- Мобильный профиль: 390×844, DPR 1, CPU ×4, заданная задержка сети 150 мс, download 200 000 байт/с, upload 93 750 байт/с. Desktop: 1440×900, без искусственного замедления.
- HTTP-кэш отключён; новый page для каждого прогона, браузер и сетевые соединения могли переиспользоваться. Это не полный cold start DNS/TLS и не эмуляция конкретного телефона. Мобильный viewport не означает отдельный мобильный User-Agent.
- Наблюдение страниц до `load` + 6 с. Один навигационный прогон на URL/профиль; они показывают диагностический срез, а не распределение.
- Отдельно шесть последовательных прогонов главной без Coverage: три с обычной аналитикой и три с заблокированными доменами аналитики. Зафиксирован момент появления Vue-приложения на корневом элементе, затем клик Create room.
- Первичная проверка Coverage выполнялась с инструментированием и частично одновременно с навигационным аудитом. Её задержки клика 200–320 мс НЕ использованы как основной результат; повтор без профилировщика дал 80–128 мс.
- Это **не оценка PageSpeed, не Lighthouse score и не CrUX p75**. Полевой INP не измерен. Приватные комнаты, авторизованные сценарии, длительная игровая сессия, все языки и все страницы сайта не проверены.
- До перехода на ручной аудит PSI не вернул отчёта, прямой API ответил 429; CrUX API был запрещён ключу, Search Console отказал в доступе. Эти ошибки ничего не говорят о скорости сайта. После уточнения пользователя SeoMonster не использовался.

На mobile суммарное превышение длинных задач над 50 мс за окно наблюдения — 309–385 мс. Это вспомогательная сумма, **не Lighthouse TBT**. Ошибок JavaScript `pageerror` в десяти навигационных прогонах не зафиксировано.

Google определяет хорошие полевые показатели как LCP ≤2,5 с, INP ≤200 мс, CLS ≤0,1 на 75-м перцентиле, отдельно по типам устройств. Низкие лабораторные LCP/CLS здесь не доказывают прохождение полевых CWV: [Web Vitals](https://web.dev/articles/vitals).

## 1. P1 — сократить период до гидратации и обработать ранний клик

**Доказательство:** ранний клик по видимой Create room потерялся. В трёх повторах без профилирования Vue mount: 4858 / 4710 / 4753 мс; медиана **4,75 с**. После mount первый измеренный клик: 80 / 128 / 80 мс. INP реальных игроков из этого не выводится.

**Причины в коде:** `main.ts` ждёт `router.isReady()` и все полные стили через `fullStylesReady()`. Общий router синхронно импортирует Lobby, поэтому его зависимости входят и в загрузку wiki. `App.vue` синхронно импортирует AuthModal, CredentialsModal, AchievementPopupsContainer и другие компоненты оболочки.

**Предложение:**

1. Для статей сделать Lobby отдельным маршрутизируемым чанком; сохранить prerender и проверить загрузку главной после изменения.
2. Перенести тяжёлую начинку диалогов в асинхронные чанки, оставив лёгкий постоянно работающий обработчик открытия. Нельзя просто лениво загрузить компонент с подпиской `mounted`: первое событие открытия иначе тоже потеряется.
3. До готовности кнопки показывать реальное состояние загрузки/недоступности либо поддержать один безопасно отложенный пользовательский intent. После mount выполнить его однократно. Не создавать впечатление, что готовая кнопка не работает.
4. Не удалять ожидание CSS вслепую: оно защищает диалоги и маршруты от отображения без стилей. Сначала уменьшить глобальную зависимость от CSS.

**Проверка:** клик в первые 0,5–1 с должен приводить к понятному состоянию и одному открытию формы; затем повторить измерения mount и клика без Coverage. Рабочая цель для этого же профиля — mount менее 3 с, которую ещё нужно подтвердить после изменений.

Файлы: `packages/ui/src/main.ts`, `packages/ui/src/helpers/critical-css.ts`, `packages/ui/src/router/index.ts`, `packages/ui/src/App.vue`.

## 2. P1 — миниатюры вместо 1024×1024 в иконках

**Доказательство:** `PreviewLink.vue` показывает значки 24×24, но `PlayerIcon.vue`, `AddonIcon.vue` и `loyalty-icons.scss` используют оригиналы через SCSS `getImagePathByID`.

| Картинка        | Production-файл | Пробный WebP 96×96 |
| --------------- | --------------: | -----------------: |
| Merlin          |        69,1 КиБ |           1,43 КиБ |
| Percival        |        80,8 КиБ |           1,52 КиБ |
| Синяя команда   |       212,8 КиБ |           4,10 КиБ |
| Красная команда |       139,8 КиБ |           3,26 КиБ |

Проба выполнена Sharp, quality 80, без изменения исходных файлов. Это демонстрация потенциала, не утверждённый визуальный результат. Для больших карточек и увеличенного CSS-кропа нужны отдельные размеры; 96 px нельзя применить ко всем контекстам.

На mobile за окно проверки изображения storage загрузились примерно на **820 КиБ на главной**, **1106 КиБ на rules**, **482 КиБ на Merlin**. Суммы взяты из Content-Length ответов, не из Resource Timing: у storage нет Timing-Allow-Origin, поэтому нулевой encodedBodySize в этом API не означает нулевой трафик.

**Предложение:** расширить существующий генератор превью и применять размер по назначению: иконки 64/96/128, аватары/карточки — больше, полноценные портреты — отдельно. Уже есть `generate-avatars.cjs` и `getAvatarPathByID`, но их 512 px избыточны для 24 px, а SCSS-иконки вообще обходят этот путь. Сохранить оригиналы для крупных иллюстраций. Для `<img>` предусмотреть width/height, srcset/sizes; для CSS-фонов — специализированные миниатюры. Изображения вне первого экрана загружать по необходимости.

**Ожидаемый эффект:** подтверждённый потенциал уменьшения конкретных иконочных файлов на 95–98%; экономию всей страницы измерить после внедрения. Это выше по приоритету, чем смена формата всего каталога на AVIF.

## 3. P1 — не загружать premium-анимации до необходимости

На `/support/` загрузились **1317,5 КиБ** изображений. Две анимации `puppeteer` и `eclipse-queen` — 637 026 и 631 898 байт, то есть около **1,21 МиБ** вместе. В измеренном мобильном DOM они были на y≈1756, далеко ниже 844 px первого экрана, размером 154×154, при исходных 512×512. У `<img>` loading=`auto`.

**Предложение:** ставить `loading="lazy"` для иллюстраций ниже первого экрана; для гарантированного отсутствия запроса до раскрытия premium-секции — назначать src/монтировать галерею при открытии. Native lazy loading может начинать загрузку заранее, поэтому сам по себе не гарантирует экономию этих 1,21 МиБ. Статичный постер до просмотра анимации дополнительно уменьшит декодирование. Не делать ленивыми LCP-изображения над сгибом.

Файлы: `packages/ui/src/pages/support/SupportBenefits.vue`, `PremiumCollection.vue`, `packages/ui/src/components/user/Avatar.vue`. Production 63.7.0 и локальную 63.8.0 необходимо сравнить перед внедрением: разметка могла измениться.

## 4. P1 — заменить полный Material Icons font

Загружается `MaterialIcons-Regular.d1b99623.woff2`: **125 116 байт (122,2 КиБ)**. Полный CSS пакета импортируется первой строкой `main.ts`; upstream использует `font-display:block`.

LayoutShift attribution показывает `dark_mode`, элементы шапки, `add`, `arrow_forward`, а на support — суммы тарифов рядом с иконками. Это согласуется с заменой шрифтовых лигатур; отдельный изолированный эксперимент нужен, чтобы приписать шрифту весь сдвиг.

**Предложение:** использовать SVG только нужных иконок, как уже сделано для Font Awesome в `plugins/vuetify/icons.ts`, с фиксированным боксом. Альтернатива — subset шрифта. Простая замена block на swap может показать текст `dark_mode` и не решает лишний трафик. Полное удаление font-запроса уберёт 122,2 КиБ; чистая экономия будет меньше на размер добавленных SVG.

## 5. P2 — сократить общий CSS и JS

Production: vendor JS **216,9 КиБ gzip**, app JS **49,4 КиБ**, английский словарь **34,4 КиБ**; всего **300,7 КиБ**. Общий vendor CSS: **58,3 КиБ gzip / 417,2 КиБ распакованного текста**. App CSS: **7,5 КиБ gzip / 39,5 КиБ распакованного текста**.

Coverage на главной с открытием формы: около **94,7% vendor CSS** и **55,3% app CSS** не использовано в этом сценарии. Это не разрешение удалить такие правила: они нужны другим маршрутам, состояниям и диалогам.

**Предложение:** после отделения Lobby и диалогов проверить реальные чанки; уменьшить стили импортируемых Vuetify-компонентов и иконочного пакета. Избегать слепого PurgeCSS: динамические классы Vuetify, темы, локали и телепортируемые модалки потребуют защиты. Важнее уменьшить общий набор компонентов, чем добавлять ещё один оптимизатор.

`check-bundle.cjs` успешно прошёл на имеющемся локальном dist: начальный JS 266,3 КиБ gzip, с английским 300,7 КиБ. Свежая production-сборка в рамках аудита не запускалась. В текущем бюджете учитывается не весь путь до интерактивности: нужен отдельный бюджет начальной страницы со словарём, route chunk, стилями, иконками и сторонними скриптами.

## 6. P2 — отложить некритичную аналитику

GA и Метрика запускаются из head. У Метрики зафиксированы tag.js **93,0 КиБ gzip**, tag_phono.js **12,7 КиБ gzip**. Async не устраняет конкуренцию за сеть и CPU.

В последовательном диагностическом сравнении блокировка доменов Метрики/Google снижала медиану времени mount с **4,75 до 3,26 с** — примерно на **1,50 с**. Это не гарантированный выигрыш будущего релиза: блокировались сразу несколько доменов, три прогона не исключают сетевую вариативность. Нельзя отдельно приписать эффект GA или Метрике.

**Предложение:** оставить лёгкую очередь событий сразу, загрузку некритичных счётчиков перенести после активации интерфейса/в idle с ограниченным таймаутом. Проверить ранние уходы, page_view, порядок событий, исключение password-recovery и отсутствие дублей. Не переносить всю инициализацию исключительно на первый пользовательский клик — это может ухудшить сам клик.

Файлы: `packages/ui/const.js`, `packages/ui/public/index.html`.

## Что уже сделано хорошо

- Production отдаёт содержательный prerendered HTML и критический CSS; первый текст не ждёт Vue.
- Гидратация публичных страниц сохраняет готовый DOM; не нужно заменять её повторным mount.
- HTTP/2 и gzip реально подтверждены ответами сервера.
- Хэшированные JS/CSS/fonts и storage-картинки имеют `public, max-age=31536000, immutable`.
- HTML имеет `no-cache`, что позволяет проверять актуальность после релиза; это не `no-store`.
- Локали вынесены в чанки, большинство страниц динамически импортируются.
- Изображения вынесены из JavaScript в отдельные файлы.
- CLS в коротких тестах низкий; переписывание вёрстки ради CLS сейчас имеет меньший приоритет.
- Портрет Merlin уже резервирует aspect-ratio в CSS. Отсутствие width/height у общего SchemaImage само по себе не доказывает CLS на этой странице.

## Проверка результата и мониторинг

1. Сохранить текущие артефакты как baseline. После каждого изменения делать минимум 3–5 последовательных запусков в одинаковых условиях, без Coverage, сравнивать медианы; отдельно холодный и тёплый кэш.
2. Контролировать ранний клик, создание/вход в комнату, меню, переключение языка/темы, фильтры, раскрытие premium и формы. Приватные игровые сценарии требуют отдельной авторизованной проверки.
3. Проверять не только LCP: mount/готовность действий, длительные задачи, реальные interaction events, байты до первого взаимодействия, CLS при приходе данных и прокрутке.
4. Добавить сбор `web-vitals`/attribution в существующую аналитику: LCP/INP/CLS по версии, шаблону маршрута и типу устройства. Идентификаторы комнат/пользователей и секреты URL не отправлять. В исходниках текущего проекта такой сбор не найден.
5. Оценивать p75 на реальном трафике; цель — LCP ≤2,5 с, INP ≤200 мс, CLS ≤0,1. Для SPA не трактовать обычные CWV как автоматические метрики каждого клиентского перехода: смена маршрута не равна новой навигации документа.
6. Brotli/CDN проверять следующим этапом при наличии географической проблемы или большого текстового трафика. В текущем срезе нет оснований начинать с замены сервера: главный доказанный резерв находится во frontend-ресурсах.

Рекомендуемый порядок: **миниатюры и отложенная premium-галерея → SVG-иконки → отделение Lobby/диалогов и ранний клик → расписание аналитики → повторные измерения и RUM**. Обработку раннего клика можно выполнить отдельным небольшим исправлением сразу.

Артефакты: `measurements.json` — данные браузера без заголовков cookies и сетевых URL с query; `mobile.png` — снимок после раннего клика. Отчёт описывает конкретные проверенные страницы, а не выдаёт непроверенные игровые сценарии за полный аудит всех состояний приложения.
